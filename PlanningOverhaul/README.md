# Planning Overhaul 1.1.0

Planning Overhaul makes layered construction plans visible and adds native building relocation through designated staging areas.

Open the panel from the Planning icon in the top bar, or from **Construction Plan** inside the vanilla Planning window. Opening from the top bar now turns on the Planning overlay automatically. Add or select a room, search the construction catalog, and choose **Plan this building**. The panel remains open while the normal Stardeus placement ghost and rotation controls are active. One right-click deselects the building.

Plans keep separate floor and upper layers. A floor can remain under a wall, door, or equipment ghost. Drawing a new building over an existing ghost in the same layer removes the earlier ghost, so a door can be painted over a wall line. Saved multi-tile buildings use Core's detailed construction rendering over a lighter footprint in their assigned Planning color. Lower-layer floor and wall roots are hidden beneath the complete upper-building footprint so their one-tile sprites cannot overwrite the split building image. **Plan Eraser** uses the vanilla Planning eraser and removes ordinary Core Planning cells plus only the highest semantic Construction Plan layer present across the complete click or drag selection. If any upper-layer ghost is highlighted, floors throughout that selection are preserved. Staging designations remain intact.

The top-bar widget opens both Planning and Construction Plan. The Build catalog follows Core's own construction-menu categories, ordering, and translated labels, including normally registered buildings from other mods and any future categories. Each category has an independent collapsible five-row scroll list, while a search opens only the matching categories. Every catalog entry keeps the building's own preview icon. Text fields keep independent values, and Enter adds and selects a room from the New room name field.

Planning Overhaul expands Core's five Planning brushes to 384 colors generated from the same hue, saturation, and luminosity space as Paint. The Build tab can key the overlay by room or by building type. Room mode remains the default, while building-type mode gives every building definition in the active plan a separate color until the palette is exhausted. Room rows, recent-entry rows, and map labels show the corresponding key color. This affects only the Planning overlay and never paints constructed floors, walls, or equipment.

The **Upgrade** tab reads the current vanilla selection. Its selection and compatible-replacement headings remain open rather than adding collapsible controls around a single working list. Select a constructed wall or floor and use Core's **Select Similar** action to select matching structures visible on screen. The tab then lists every currently unlocked definition on that layer that Core considers a valid replacement. Choosing one queues Core's normal replacement task at every compatible selected position, preserving each structure's rotation. Walls and doors share the wall layer; equipment is intentionally excluded because it does not have a general compatibility rule.

Upgrade replacements retain Core's normal material costs, work, cancellation, and configuration-copy behavior. A structure with another active task or an incompatible location is skipped and reported in the panel status instead of receiving a custom forced replacement.

The Rooms tab keeps the Room sequence inside a seven-row scroll list, so large blueprints do not push room editing, creation, and reset controls far down the panel. It can delete the active room after a second confirmation. This removes its remaining plan entries while preserving completed buildings, and waits only for genuinely active construction, relocation, or plan-issued deconstruction work; completed staging moves no longer leave a room falsely locked. **Delete all rooms** is a separate confirmed reset that cancels every tracked Planning Overhaul construction, replacement, relocation, and deconstruction task, clears the room plan, and creates a fresh empty Room 1 while preserving completed buildings and staging designations. Choosing a planning building automatically pauses the game and keeps it paused until that building is deselected. If the mod paused an actively running game, the previous speed returns when placement ends; a game that was already paused stays paused.

While choosing a building, the moving live placement preview and the saved construction ghosts now share Core's temporary tool layer. The preview temporarily occupies only its current cell, and the saved ghost beneath it returns as soon as the cursor moves away. This keeps the rest of the blueprint visible throughout placement.

The Blueprints tab can create a Construction Plan from the currently constructed ship. It scans the island containing the Ship Computer (or the largest constructed island), turns Core's enclosed areas into separate captured rooms, places attached outdoor devices in an Exterior room, and preserves every captured building's rotation. Capture replaces the current plan after a second confirmation; use the existing name and Save Blueprint controls to retain it for another run. Long Construction Order and Status messages use wrapped framework-owned rows so their full text remains visible.

Captured rooms inherit the explicit room names shown by Core's Rooms overlay. Unnamed areas keep the `Captured Room N` fallback. New ship captures and imported blueprints order enclosed rooms by the distance from each room's planned floor center to the plan's geometric center, moving outward in concentric sequence; rooms at the same distance continue around the center, and Exterior follows the enclosed rooms. An import selects the newly ranked center-most room. The Rooms tab and Continuous construction both use this sequence without changing the construction phase scheduler. Selecting any populated room in the Rooms tab opens the Planning overlay and focuses the camera on the full planned footprint for that room. While Planning is visible, each populated plan room displays its name on the actual planned floor cell nearest the room's center of mass, with the active room highlighted.

The **Pulse Wave** tab shows the selected room's remaining structural cost. Its unavailable-action explanation uses a full-width wrapped row so both the action and reason remain readable. A wave can start only while Continuous construction is off and only when every material has the normal cost plus a rounded-up 10% buffer. A wave queues floors, walls, and doors through Stardeus's normal construction and replacement commands; the buffer is checked but not consumed. Walls and doors above angled, partial, or missing floor tiles wait for a planned full-floor replacement at those positions, including supporting floors assigned to adjoining rooms. If no supporting full floor is present or planned, the status identifies that missing prerequisite.

All panel actions now use icon identifiers present in the current Core build. This removes the repeated unavailable-sprite warnings that could misleadingly carry the pooled row's previous **Plan Eraser** label; the eraser itself continues to use the vanilla Planning eraser.

The **Staging** tab provides rectangle drawing tools for **Indoor**, **Outdoor**, and **Outdoor Edge** areas. Indoor cells become usable after their floor is finished; ordinary equipment moves do not require enclosure or oxygen unless Core explicitly marks the building as requiring indoors or outdoors. Every building sent to Indoor staging reserves its complete footprint plus a one-tile perimeter that must remain inside the designated staging area on clear floor, keeping doors and walking routes open. Outdoor staging accepts exterior open space and completed exterior floor; Core's native placement rule selects the compatible support for each building, and a building with Core's **Must be outdoors** component is routed there even when it is floor-based. Outdoor Edge cells remain open space beside a finished floor. A constructed building whose complete footprint is already inside any current staging designation is treated as a staging occupant rather than unplanned room clutter, even where staging overlaps a planned room. This coordinate check uses the live staging sets on every room pass, so drawing or erasing staging changes that protection without cached ownership. When a structural destination is occupied, the wave first moves a compatible relocatable building directly to a planned destination whose local structure is already complete, then considers the matching staging type. Planning Overhaul admits only one active move into staging at a time because each new staging position depends on the current layout. Direct moves to ready final blueprint destinations, including returns from staging, fill one shared priority-5 relocation pool capped at half the living player-faction crew, rounded down with a minimum of one. Background moves create Core's native relocation targets and jobs without activating the player's placement tool, changing the current selection, closing an unrelated building panel, or playing manual placement feedback. Core can queue those relocation jobs while another component on the source building owns a crafting, operating, or material-hauling task. Configured production buildings move only when a connected, reachable, producing power network has an available connector at the destination; Planning Overhaul passes that connector to Core for reconnection after placement. Core preserves their recipes, held ingredients, demand counters, and partial crafting progress through relocation. No stowed building form is used.

Continuous construction selects work by stage across the complete plan. It checks the next room or phase every 24 game ticks, one fifth of the previous interval. Enclosed rooms progress through structure, clearing, connected power, construction support, atmosphere, and ordinary equipment. Exterior uses a separate floor-frontier policy described below. A later equipment shortage cannot hide new structural work in the same or another room. New floor construction is submitted in bounded batches only from planned positions cardinally adjacent to an already-built floor. Detached planned components are never submitted as floating construction ghosts. A room without a valid floor frontier yields so later rooms can progress; after a complete validation pass, construction halts with an actionable status until the player connects the blueprint or builds the required supporting floor. Core then controls worker availability, reachability, hauling, and completion. New or resumed plan construction starts at priority 3, but a positive priority selected by the player remains unchanged during later planning checks. Completed floors are promoted within Planning Overhaul's queue so newly reachable work is inspected first without repeatedly scanning the blueprint interior. Deferred structural queues keep one material budget across all bounded submission ticks, subtract existing plan-issued demand, and clamp that budget when live inventory falls. They stop at the current material limit while retaining the 10% buffer. Each planning inspection builds one short-lived occupancy snapshot from planned floor positions and Core's active relocatable-building registry. Clearing and reusable-equipment lookup share that snapshot instead of scanning complete wall and object map layers, while every chosen building is still checked against live state before an order is issued. A building already at the correct destination and rotation is left alone. Otherwise, the scheduler first reuses a matching movable building; when no reusable copy is available, it queues a new one through normal Stardeus construction. Exact-conformance clearing remains limited to 24 relocation or deconstruction orders per automation pass.

Nanobot Hives and every blueprint-authored Quantum Storage endpoint are handled as Power-phase construction support in enclosed rooms after their connectors are built and connected. When Quantum Storage is installed and both the Nanobot Hive and Quantum Storage research are unlocked, a separate optional pass can add a missing Hive and raw-material Quantum Storage Unit to a room that does not already plan them. It uses only completed, vacant planned floor cells that are outside every future non-floor blueprint footprint and within reach of a connected, reachable, producing power connector. The ordinary cost plus the 10% reserve must already be available. Exterior support follows its live floor frontier. A greedy coverage pass selects the farthest completed planned floor outside current Hive range, places the next Hive within range of both that target and an established Hive, and completes its nearby Quantum Storage pairing before extending again. Each successful Hive therefore covers at least one new target; the blueprint footprint, available powered space, and native placement rules determine the practical pair count instead of a fixed twelve-pair ceiling. Enclosed rooms still receive at most one pair.

Optional support is a bonus, never a room requirement. Missing research, materials, power, or safe space lets the room continue. Enclosed rooms can be reconsidered by stopping and starting Continuous construction; Exterior retries periodically as its floor frontier and powered space change. Added helpers use Core's native construction, power connection, hauling, workers, and Nanobot behavior. They remain as ordinary ship infrastructure, survive save/reload without being mistaken for clearing clutter during the active plan, and stay outside reusable blueprint data unless the finished ship is captured again. Quantum Storage is detected from its registered definitions at runtime; it is not a dependency and its DLL is not referenced.

When a room is waiting only on Planning Overhaul work already present in Core's task list, the scheduler records that task state and yields the room so later rooms can start available work. A room with active equipment construction can still queue eligible equipment moves, but it receives no additional construction orders until its existing construction finishes. Optional Nanobot Hive and Quantum Storage support follows the same gate. Task assignment, worker movement, construction progress, relocation progress, completion, and newly queued work count as observed changes. If a complete room pass queues nothing and observes no change in the remaining active tasks, Status and a one-time warning ask the player to investigate the native tasks and advise: **Stop and start Continuous Construction to clear the cache.** Continuous construction remains enabled and continues periodic passes; the same unchanged task state does not repeatedly open the warning.

Continuous room clearing checks each building's blueprint position and rotation before moving it. A displaced building searches for a missing, safe final destination across all blueprint rooms, with same-room destinations preferred, before compatible staging is considered. Ordinary equipment construction and relocation, including moves into or out of staging, use Core placement rules without enclosure or oxygen requirements. Core still checks the required floor, footprint, and native placement constraints. Staged buildings also check clear final destinations across the blueprint before further room clearing, retaining the destination room's construction phase order. A staged building already matching the blueprint stays in place. Clearing status reports direct moves separately from staging moves.

Ship Computer and Quantum Ship Computer buildings are never deconstructed or destructively replaced by Planning Overhaul. A computer that does not block an unfinished blueprint destination stays where it is. If one blocks required construction, the planner may move it through Core's native relocation system, preserving the building instead of demolishing it. Planned Ship Computers remain constructible. In Sandbox instant-build mode, an occupied floor replacement waits for the wall or equipment above it to relocate or clear first, preventing Core's temporary floor-removal check from dismantling the Ship Computer or another supported building as a side effect.

Stasis Array, Particle Collector, every Core chess piece, and Mysterious Statue (Core's Pentagram Statue definition) are protected special originals. Planning Overhaul can relocate them but never orders their deconstruction, replaces an occupied special original, or constructs a replacement copy. Stasis Array and Mysterious Statue require an enclosed indoor destination with at least Core's minimum oxygen across their footprint, including when sent to staging. Particle Collector requires an exterior-edge destination attached to completed floor and must pass Core's rotated placement rules. Chess pieces can use indoor or outdoor final destinations under Core's normal placement rules, without an atmosphere gate; compatible staging considers both Indoor and Outdoor. Indoor staging retains its one-tile clearance. If a suitable destination is unavailable, the original stays in place and Status names the building, coordinates, and requirement. The scheduler processes other available room work, then checks other rooms before retrying. On load, saved planner-owned demolition and replacement orders for these originals are cancelled through Core; player-issued native orders remain under player control.

A protected original outside the blueprint requires work only when a matching blueprint destination is missing or it actually blocks an unfinished planned placement. Surplus originals remain where they are and do not prevent completion. Sharing a floor or another layer does not itself require relocation: Core can accept supporting sockets or other structure beneath the original. Protected originals wait at their current position for final destinations; staging is considered only when they must clear a blocked planned placement. Completion status lists the protected originals retained outside the blueprint.

When required protected work cannot progress, Status identifies the missing blueprint destinations or blocked buildings, with room names and coordinates. Failed destination checks identify missing support, enclosure, oxygen, occupied cells, rotation differences, native placement rejection, current work, or Advanced Relocation research. After a complete pass without starting more work, Continuous construction performs one final validation pass. If that also cannot start work, Status reports a halt with counts of unfinished structural rooms, unfinished equipment entries and buildings requiring clearing, plus up to four outstanding blueprint entries and their reasons. The planner retains the originals and rechecks periodically; actual progress, blueprint edits, or a Continuous construction toggle reset this validation state.

Material shortages are the exception to room completion. Within the current structural or equipment stage, Continuous construction selects every entry it can fund while keeping the rounded-up 10% stock buffer, queues those affordable entries, and records the remaining shortage. The material gate covers up to 64 new equipment orders at a time. Manual Pulse Wave keeps its stricter rule and still requires the complete remaining structural wave plus its buffer before it starts.

After publishing a material shortage, the scheduler yields that room and continues forward through the configured room sequence at the earliest available stage. It wraps to the start after reaching the end and repeats while another room can begin work. A complete rotation that cannot start anything locks onto the material-blocked room with the earliest stage, then uses room order. While locked, the Material gate retains the pending building list and recalculates the complete batch cost from live inventory after subtracting the missing materials already committed to plan-issued construction ghosts. The wait performs a bounded periodic recheck even while other jobs remain active in that room. It resumes as soon as one waiting building can be funded with its own 10% buffer, without requiring every earlier job in the room to finish first.

The captured **Exterior** room is stored as a semantic room type, so renaming it does not remove its special behavior. Its only structural prerequisite is connected floor construction. Every other planned entry—including walls, doors, power connectors, atmosphere devices, and ordinary equipment—belongs to one post-floor pool. As soon as an entry's complete footprint has its exact completed planned floor, it may be cleared, relocated, reused, or constructed while the remaining Exterior floor continues expanding. A building designed for open space becomes eligible when its footprint has adjoining completed floor and Core accepts the attachment. Power and atmosphere infrastructure can still be built, but neither category gates unrelated Exterior work. Research-locked or temporarily unaffordable Exterior buildings do not freeze the floor frontier. Core placement, material, reachability, powered-production relocation, and cardinal floor-adjacency rules remain in force.

When every room matches its blueprint and the remaining plan construction, relocation, and deconstruction jobs have finished, Continuous construction turns off automatically. A warning popup confirms that the Construction Plan is complete and Continuous construction has been disabled. Finishing one room or waiting for materials or staging does not trigger this popup.

After each complete room rotation, four separate configuration passes restore crafting queues, Transporter names and internal links, installed upgrades, and planter settings. Each pass keeps its Status visible for one full 24-tick automation interval. If settings remain incomplete, the final rotation Status reports the number of waiting buildings in each configuration category and the first concrete wait from each category. When Auto Factory is loaded, Planning Overhaul excludes the dynamically owned production queues on Nano Fabricators, Nano Foundries, and Nano Cloning Pods from new captures and ignores any saved queue metadata for those buildings in existing PO4 blueprints. Their other saved settings remain available. The optional check uses no Auto Factory type reference, and normal queue retention remains active when Auto Factory is absent. The planter pass retains the selected crop and Auto Harvest choice for Mini and Large Planters through Core's normal planter controls. It does not copy plant growth, spawned plant instances, stored water, or harvest progress. A configuration wait never holds a room turn; unfinished settings are retried after the next full room rotation. PO2 and PO3 blueprints contain no planter metadata, so constructed planters from those plans remain unconfigured and produce a persistent status warning that asks for a fresh capture from the original ship.

While waiting for those final jobs, Status shows the pending job count and up to four examples with building names, map coordinates, room names, current native tasks, task states, assigned workers, and priorities. Relocation examples include the source and destination when available. Failed tasks include Core's last failure reason, and a relocation with no active task is identified explicitly. The count includes each building once, even when its relocation destination is also tracked as construction.

Status and other wrapped information rows grow to fit the text at the current panel width. Short status messages retain enough space for a complete line, and the full message remains available in the tooltip. If no status message is available, Status displays the current Continuous construction mode. During unpaused construction, the Staging and Pulse Wave tabs update their live counts, summaries, material details, and Status text in place instead of rebuilding the complete panel, so tab and collapsible-section input remains responsive.

During structural queuing and construction, Status also shows up to four current floor, wall, or door jobs with their building names, coordinates, native task states, workers, priorities, and reported failure reasons. Each game tick checks that the displayed jobs remain active and pending; finished or removed jobs are replaced by another available example. A construction ghost that has lost its Core task receives a new native hauling or construction job through Core's normal job creation path. When no task can be retained, Status identifies the affected building and coordinates instead of showing a generic recheck message. The search uses a snapshot of tracked job IDs refreshed during normal structural automation, with at most 64 candidate checks and a one-millisecond search budget per sampling pass. It does not scan the full blueprint each tick. Status text and its tooltip update when the message changes, without rebuilding the entire panel or changing any construction jobs.

An empty structural submission queue is rechecked against the room's remaining plan. Cancelled or removed construction ghosts can be submitted again through the normal placement and material guards. Active structural ghosts no longer stop the scheduler from submitting other unlocked, affordable structural entries in that room; compatible occupied floors, walls, and doors enter Core's native replacement path inside the same bounded batch. The batch still counts existing plan-issued material demand and preserves the stock buffer. While viable native construction or replacement jobs remain, Continuous construction keeps that room active. New floor ghosts remain paused until their position is cardinally adjacent to a completed floor, preserving Core's connected-construction restriction. A replacement that lost its Core task is cancelled and reissued through Core's native replacement command before room rotation is considered. A room whose remaining floors have no completed neighbor, or whose walls and doors still lack completed floor support, releases the active-room lock so later structural rooms can be checked. If every incomplete room is blocked by the same disconnected-floor condition, a final validation pass halts automatic submission, names the affected rooms, and periodically rechecks without creating floating tiles. The room also yields when its remaining work is material-limited or no native task can be restored. An enclosed room whose shell is complete can continue through clearing, power, atmosphere, and equipment while other rooms still need structural work. Exterior instead admits locally supported post-floor work during its continuing floor expansion. Status distinguishes active construction and replacement tasks from pending relocation or deconstruction jobs and names deferred floors, walls, doors, and their room-owned support where available.

Displaced walls and doors can move directly to matching vacant blueprint locations on completed full floors. Structural queuing reuses an eligible existing wall before constructing a new copy, and moves a reusable wall away before replacing its old cell. Wall clearing and reuse match structural completion by building type and position, preserving correctly placed walls despite saved rotation differences. Core handles connected wall graphics and automatic wall orientation; equipment retains its blueprint rotation check. A wall still needed at a destination that is not ready remains in place. Once its matching destinations are filled, surplus walls receive native demolition orders without a staging trip. Planned wall footprints are protected from surplus demolition so clearing cannot create a wall removal and reconstruction cycle. The wall source index is prepared incrementally within the existing structural batch time budget and is revalidated during reuse. Native relocation rules and priority 5 remain in use.

A room yields after a complete clearing scan cannot queue any relocation, deconstruction, or structural work. This includes mixed blocker sets such as buildings finishing current work alongside other buildings waiting for compatible staging or a powered final destination. Before yielding, Continuous construction still attempts ready staged returns, reusable-building moves, and independently buildable equipment in that room. The unresolved clearing candidate is then recorded for the current rotation and the other rooms are checked in sequence, allowing later construction and organization to make final destinations available. A structural or equipment phase that requires unfinished research also yields its room without bypassing the research restriction. When every unfinished room has yielded to relocation constraints, Continuous construction clears the blocked-room set and performs one final room-by-room validation pass. It reports a halt only if that second complete pass still makes no progress, then periodically rechecks so changed tasks, powered destinations, or staging capacity can resume the plan. The Pulse Wave status identifies the active Continuous room and reports building names, coordinates, and the specific wait: research, materials, active work, placement validation, power connection, atmosphere, or staging capacity. The status distinguishes the serialized one-at-a-time staging admission limit from the larger crew-scaled final-destination relocation capacity.

While Continuous construction is preparing a new power, atmosphere, or equipment batch, the Material gate lists every building type in that batch with its count and planned locations. The material rows show the batch's normal build cost, buffered start requirement, current stock, and shortage. Structural work continues to show the selected room's Pulse Wave requirements in the same section. While the game is paused, manually selecting a room makes Status and the Material gate inspect that room and display its retained material wait using current inventory counts. Unpausing returns both displays to the room Continuous construction is processing. When a room's planned power connectors are built but not yet connected, that room remains in its power phase and yields its turn. Later rooms continue through the rotation, and the blocked room is rechecked after the cursor returns to it.

If Auto Factory is loaded, each material-blocked Continuous room publishes native construction `Lacking materials` requests for its missing material types. These requests remain active while the scheduler works through later rooms, allowing Auto Factory's Global facilities to keep producing through their normal recipes and production orders. Planning Overhaul refreshes the requests whenever an affordable portion starts and clears them when no room is waiting for that material or Continuous construction is turned off. Auto Factory remains optional and is not a Planning Overhaul dependency.

The active plan and all three staging areas are part of the game save. Named reusable plans are stored under Stardeus's persistent-data `PlanningOverhaul/Blueprints` folder. New `PO5` blueprint codes include durable Exterior room metadata, the original map width and height, retained production configuration, installed upgrades, Transporter names and internal directed links, and planter crop and Auto Harvest settings alongside the compressed, integrity-checked room, placement, and staging data. Existing PO1 through PO4 codes remain supported; older rooms named Exterior are migrated to the semantic Exterior type when loaded. Imports preserve each building's tile coordinates relative to the map center, including its full rotated footprint, then recalculate the center-out room sequence on the adapted layout. A blueprint may move between different map sizes when every saved building footprint, Transporter target, and staging cell fits the centered current map. When reducing the map size, planned content must also stay out of the current map's corner no-build zones. The blueprint is never scaled, clipped, or wrapped; any content that would not fit causes the import to fail before replacing the current plan. Building sizes are read once per definition and rotation during import.

Older `PO1` files do not contain their original map dimensions and are no longer importable. The planner does not guess those dimensions. Loading an existing game save keeps its active plan at its saved positions and retains its native job ownership.

The Blueprints tab uses collapsible **Create from constructed ship** and **Save/Load blueprint** workflows. Copy blueprint code reads the current active plan directly and does not require a saved file. **Clear blueprint from plan** is a confirmed action inside Save/Load blueprint. It removes all planning rooms, building ghosts, staging marks, persisted Planning Overhaul palette values, and stale split-sprite fragments and turns Continuous construction off. It also clears older Core-color planning marks at known blueprint footprints while preserving unrelated Core planning cells. Saved blueprint files, constructed buildings, and existing native jobs remain intact. Plan Eraser clears ordinary Core Planning cells and removes the highest Construction Plan layer in a click or drag selection while preserving underlying floors and staging; a selection containing neither type now reports that explicitly.

Saved blueprints appear in a bounded scrollable list. Each saved blueprint has a delete button using Core's demolition icon on the right of its load row. This deletes only that blueprint's `.pob` file and refreshes the list. The active Construction Plan and its jobs remain unchanged. A status message reports the result or a file error.

## Release status

### Local hardening pass (version remains 1.1.0)

- Separated blueprint serialization, equipment-state inspection, and relocation candidate selection into dedicated modules. Added comments around cache lifetime, persisted ownership, scheduling cadence, and native validation boundaries.
- Blueprint encoding reuses one stable entry ordering. Decoding indexes metadata targets instead of searching the entire plan for each setting; the latest preceding duplicate entry still wins. PO1–PO5 handling and PO5 output are unchanged.
- Equipment inspection uses indexed per-room structural lists and stops after the first missing structure in each room. A revision-invalidated view caches only which entries are post-floor work; live completion, power, occupancy, staging, and placement remain freshly checked. Original post-floor entry order is retained.
- Paused Pulse Wave material/status inspection shares one local equipment snapshot instead of rebuilding it twice.
- Relocation discovery uses the definition index for ordinary staged returns as well as direct returns. Preferred destinations/sources are checked first, avoiding power and occupancy checks for farther unused candidates. Direct returns at capacity skip destination discovery; final admission and Core validation remain intact.
- Removed the unreferenced ghost-refresh helper, unused equipment-state constructor, duplicate phase wrapper, and obsolete paused-UI room field.
- Diagnostic write failures, including failures while flushing/closing a broken log, no longer escape into gameplay.

Validation: the Release build passed with zero warnings/errors. The off-game harness passed 354 assertions when compared against the pre-pass routines and the existing 71,774-entry / 73-room saved blueprint. Coverage includes a synthetic 71,786-entry plan, byte-identical PO5 serialization, metadata and legacy decoding, malformed input, room/type/edit invalidation, live completion changes, stable relocation choices, and logging failures. A representative synthetic run reduced metadata decoding from 1,051 ms to 122 ms and 20 stub-world equipment inspections from 178 ms to 52 ms. These are .NET 10 harness timings, **not Unity frame timings or an in-game FPS claim**.

The harness links production routines with minimal Core boundary doubles and is excluded from the mod assembly. From the mod directory, using the .NET 10 SDK:

```powershell
dotnet restore Tests/HardeningTests.csproj --configfile Tests/NuGet.Config
dotnet build Tests/HardeningTests.csproj -c Release --no-restore
dotnet ../.build/PlanningOverhaulHardeningTests/bin/Release/net10.0/HardeningTests.dll
```

The normal self-contained suite has 195 assertions; optional pre-pass comparison fixtures add the differential checks. Pass a `.pob` path to the executable for an additional read-only saved-blueprint round-trip check. Test binaries/intermediates are written outside the live mod directory under `Mods/.build`.

In-game acceptance remains pending after restarting Stardeus: continue the same large blueprint at the same game speed, verify room rotation, floor adjacency, concurrent final moves / single staging move, optional support, player priority retention, and stable FPS. No scheduler policy, native job authority, material/research requirement, protected-building rule, or player-selection behavior was intentionally changed. Issued-entry ownership scans, live occupancy discovery, and full overlay rebuilding are retained; removing them safely needs stronger runtime invalidation evidence, not assumptions that completed entries or cached occupancy can never change.

Version 1.1.0 expands Continuous construction into a non-blocking room scheduler. Rooms yield when research, active Core work, disconnected floor frontiers, relocation constraints, or full staging prevent useful action. Exterior follows its own connected-floor policy and can add optional Nanobot Hive and Quantum Storage support as its frontier grows. Generic functional-clearance checks identify blockers on required input and interaction cells outside a building's visible footprint. Large-plan Exterior discovery now reuses bounded candidate and footprint caches while every order still passes current world-state and Core validation.

## 1.1.0

- Reconciled room and staging overlap by checking every constructed building footprint against the live staging coordinate sets on each pass; current staging occupants are no longer cleared merely because their cells also belong to a planned room.
- Kept staging destination compatibility rules unchanged when Planning Overhaul selects a new relocation target; the coordinate rule applies only to buildings already occupying a designated staging footprint.
- Yielded equipment-stage rooms with active construction orders after checking eligible relocations, preventing one busy room from stopping work in later rooms without adding another construction batch to the busy room.
- Applied the same active-construction gate to optional Nanobot Hive and Quantum Storage support.
- Added a modular optional Power-phase construction-support pass for Nanobot Hives and Quantum Storage.
- Promoted blueprint-authored Nanobot Hives and every runtime-detected Quantum Storage endpoint ahead of atmosphere and ordinary equipment.
- Added missing Hive and raw-material Quantum Storage Unit support only when both definitions and research are available, a safe powered floor cell is free, and the normal material cost plus reserve is already affordable.
- Added a semantic Exterior room type to PO5 blueprints while retaining PO1 through PO4 import support.
- Reduced Exterior structure to connected floors; walls, doors, power, atmosphere, and equipment now enter one locally supported post-floor pool without power or atmosphere gates.
- Allowed ready Exterior clearing, relocation, construction, and support work to proceed while the remaining connected floor frontier continues expanding.
- Extended optional Exterior support with greedy Hive coverage and paired Quantum Storage placement along the completed floor frontier; every new Hive must remain reachable by an established Hive, cover a new target, fit entirely on safe planned floor, and avoid every planned non-floor footprint.
- Kept the bonus non-blocking, dependency-free, outside exported blueprint entries, persistent across save/load, and bounded by actual uncovered targets rather than a fixed exterior pair limit.
- Replaced surplus-wall relocation's full-blueprint destination scan with the definition index while retaining same-room preference, distance ordering, support checks, placement validation, reservations, and Core relocation jobs.
- Added phase timing for Exterior frontier evaluation and cached repeated capacity-plus-active-work waits. Optional support and blocker clearing still receive a full evaluation first, changed work invalidates the wait, and unchanged waits receive periodic full rechecks.
- Redirected Planning Overhaul startup, optional-support, and performance diagnostics from Unity's shared `Player.log` to a session-reset `PlanningOverhaul.log` beside `ModInfo.json`. Only failure to create the private log produces one actionable `Player.log` warning.
