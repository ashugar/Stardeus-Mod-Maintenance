# Private validation records

Run `New-ModValidationRecord.ps1 -ProfilePath <absolute-private-profile.json>` with PowerShell 7.2 or later. Copy `ValidationRecord.profile.example.json` outside the checkout and replace every placeholder and pin. All profiles and generated reports are private; they may contain local paths, descriptions and copied evidence. Nothing is redacted or uploaded.

The helper reads only explicit pinned artifacts and reports. It writes a unique run beneath an external output root, refusing overlap with source, live game data, Steam/game locations, declared roots and explicit inputs. It does not execute other helpers, load game assemblies, install files, control processes or publish.

Supported machine reports use schema 1:

| Profile Type | Report Kind | Context ID | Recorded stage | Completion rule |
| --- | --- | --- | --- | --- |
| `Baseline` | `StardeusBaseline` | `BaselineId` | `Baseline` | `Recorded` |
| `Versions` | `ModVersionConsistency` | `CheckId` | `VersionChecks` | `Consistent` or `ConsistentWithOptionalOmissions` |
| `LogAnalysis` | `StardeusLogAnalysis` | `AnalysisId` | `LogReview` | `AnalysisRecorded` alone stays open; explicit attributed `LogReview` can complete it |
| `ApiAudit` | `StardeusApiAudit` | `CheckId` | `ReferenceChecks` | `CheckedSupportedScope`, with nonempty checked reference/patch rows and consistent supported coverage |
| `Contracts` | `StardeusContractComparison` | `ComparisonId` | `ContractComparison` | `UnchangedInSelectedScope`, with nonempty consistent selected results |

`ContractComparison` records explicit API/IL structural selections. It remains separate from broader behavioral `UpstreamComparison`, which this helper does not infer. An empty API reference/patch scope is retained as `CheckedEmptyScope` and leaves its stage open. Success applies only to producer-selected, supported scope; it is not overall compatibility approval. Use the producer's context ID and SHA-256 of the exact report. Current reports must meet `NotBeforeUtc`, match subject context and bind declared artifacts. Current version evidence must include a checked root `ModInfo.json` input whose pinned `Id` matches the subject; a version number alone cannot identify the mod. `ExactPathAndHash` binds both path and bytes; explicitly selected `HashOnly` allows identical bytes at another path and requires a nonempty `Reason`. Every present file footprint in current machine evidence is rehashed, including selected game/reference inputs beyond the chosen artifact bindings; changed inputs reject the evidence. Missing selections remain report gaps and must remain absent while assembling current evidence. This covers only producer-selected files, not complete installation state. All pins are uppercase SHA-256. Required current machine evidence needs at least one artifact key. Log analysis can bind its explicitly selected log as a `Reference` artifact; this does not bind the log to a deployed mod DLL. Metadata reports require their checked root subject manifest and matching `Id`. Current diagnostic `Subject.ModId` and `Subject.Root` must match the declared record subject/roots. Diagnostic reports require bounded nonempty unique `Inputs`, each with `Status: Present` and an exact SHA256. Log producer/Common support footprints and metadata engine/support source provenance are also pinned and rehashed for current reports; a changed tool source invalidates that affected evidence. Contract row counts, side text hashes and comparison statuses are checked against reported coverage. API patch target and binding statuses are checked separately: a supported result requires resolved targets and checked supported bindings; unchecked/review-required bindings require gaps and failed bindings require findings. Unsupported or contradictory success claims are rejected. Failed/gapped API reports, changed/unresolved contracts and parser gaps remain visible and open. Fatal contract producer `Failed` reports may have empty selections/coverage but must retain failure gaps or findings; they never complete their stage. Only declared files are covered.

`Attachment` records pinned bytes without interpreting any stage. Native `release.json`, installation plans/journals and arbitrary logs are attachments: their presence never marks package, installation, startup or gameplay checks passed. Do not use unsupported Cosmoteer evidence types. Historical evidence is retained but never elevates a current stage.

A failed or unresolved machine report can be accepted as evidence while leaving its stage open. Log diagnostics, including `NoRecognizedIssues`, never automatically complete `LogReview` or elevate startup/gameplay. A supplied effective log `NotBeforeUtc` must meet the record task boundary; native elapsed clocks retain unknown freshness. An explicit `LogReview` attestation may report an agent or user review with the existing reporter, source note, current timestamp, current evidence and exact artifact-binding requirements. It must cite accepted current `LogAnalysis` evidence; each reviewed native current input must be bound through a declared `Reference` artifact included in both the evidence and attestation bindings. An arbitrary attachment cannot support this review. Review may be `ReportedPassed` or `ReportedFailed` as appropriate, and changes only `LogReview`; startup and gameplay remain separate. The helper does not infer this review or interpret log contents as an attributed runtime outcome. Use separate explicit supported attestations for actual startup, gameplay and acceptance evidence. Contradictory success claims are rejected. Log review, source review, build, startup, gameplay, save/reload, user acceptance and publication are attributed manual stages, with `Pending`, `NotApplicable`, `ReportedPassed` or `ReportedFailed` status. Reported outcomes require current accepted evidence, exact artifact bindings, reporter, explicit-offset timestamp and source note. User acceptance requires a user reporter. These are caller claims, not independently verified results or authorization. Every declared payload artifact must be bound.

The output includes `validation.json`, `validation.md`, `summary.json` and optionally copied evidence. Default behavior retains reports then fails for rejected evidence or changed/unavailable artifacts. `-RequireComplete` additionally fails for open required stages; `-ReportOnly` suppresses those final gate failures. Invalid profiles fail before output. `Recorded` describes a scoped evidence record, not overall compatibility or release approval. Validation tool and support hashes are pinned initially and rechecked before output. Evidence inputs and matched artifacts are rehashed before writing, but this is not an atomic installation snapshot.


Run isolated adapter tests after relevant changes:

```powershell
pwsh -NoProfile -File build/ModMaintenance/Tests/Test-ValidationRecord.ps1
pwsh -NoProfile -File build/ModMaintenance/Tests/Test-DiagnosticHandoffs.ps1
```

The handoff suite uses the actual log producer and intentionally crafted metadata reports to verify negative-state and contradiction handling. Actual API/contract producer handoffs are distinct integration evidence. Both suites retain private receipts with exact tool/support/test hashes; neither reads player data or runs Stardeus.
